> 状态：**草案（未生效）**。本文只提出问题、证据与候选口径，**不修改任何阈值**；
> 现行门槛仍以 `docs/61-gate-report.md §10.2.5` 与 `tests/perf/k6/exam_flow.js` 的 `thresholds` 为准。
> 需要 R0（产品/验收）+ QA 双签，才能在 CI 里改阈值。

## 1. 为什么需要讨论口径

现行 G4 性能门槛是一条**单一数字**：

```
scenario answer_save   http_req_duration p(95) < 300ms
scenario session_read  http_req_duration p(95) < 300ms
http_req_failed rate < 0.1%
```

`answer_save` 这个场景在 3 分钟里其实混合了四种性质完全不同的流量：

| # | 流量 | 触发时刻 | 并发形态 | 语义 |
|---|---|---|---|---|
| 1 | `POST /exams/{id}/sessions`（新建会话） | t≈0–2s，且 t≈5s 又一批 | **同一秒 100 个** | 开考进场，幂等建会话 + 返回 100 题 |
| 2 | `PUT /sessions/{id}/answers` | 每 30s 一波 | **每波≈100 个同时** | 自动保存，一次 10 题 |
| 3 | `POST /sessions/{id}/submit` | 末段 20% | 20 个 | 交卷 + 判分事务 |
| 4 | `GET /sessions/{id}`（读场景） | 全程 200 rps | 稳态 | 刷新/断线重连 |

把 1、2、3、4 混成一个 P95 的问题是：**1 只占 14% 样本**，但它决定 P95 的下界——
即使每一次保存都只有 30ms，只要「同秒 100 个建会话」慢到 1s，`answer_save` 的 P95 就不可能 < 300ms。
这与「系统能不能支撑 100 名学生同时考试」是两个不同的问题，用同一个数字回答会掩盖真实风险。

## 2. 证据（全部来自真实 Linux runner，非估算）

### 2.1 服务端侧拆解（run `42859094367`，4 vCPU，4 worker）

从容器访问日志的 `latency_ms`（服务端 `perf_counter` 口径，不含网络/客户端排队）重建：

| 路由族 | 样本 | p50 | p95 | p99 |
|---|---|---|---|---|
| `PUT /sessions/{id}/answers`（保存） | 580 | 110ms | **1026ms** | 1152ms |
| `GET /sessions/{id}`（读） | 34 705 | 10.5ms | **38.5ms** | 149ms |
| `POST /exams/{id}/sessions`（开场/恢复） | 200 | 754ms | **1044ms** | 1079ms |

结论 1：读侧早已达标（38.5ms）；慢的是「同秒 100 并发」的两条写/进场路径。
结论 2：k6 的数字不是压测机假象（服务端侧同样慢）。

### 2.2 冷启动贡献（同一 run，按 5s 桶）

| 时间桶 | 保存样本 | p50 | p95 |
|---|---|---|---|
| t≈20s（第一波） | 100 | **766ms** | 1060ms |
| t≈110/115s | 36 / 64 | 31 / 68ms | 66 / 185ms |
| t≈170/175s | 24 / 56 | 40 / 100ms | 112 / 237ms |

同一规模、同一负载，第一波与最后一波差 **7.7×**。→ 已用「启动预热」修复（`docs/61 §10.4.4`）：
进程接流量前填满连接池、装载冻结快照/题面视图，把冷启动从被测窗口里挪走。

### 2.3 容量测算

单请求服务端 CPU（本机空载 cProfile/探针）：读 2.7–3.2ms、开场建会话 3.1–3.4ms、
保存 10 题 ≈5.2ms（含 1 次 commit）。「同一秒 100 个开考请求」在 4 vCPU 上理论下界
≈100×3.5ms/4 核 ≈ 90ms，**但**这 4 核还要同时跑 200 rps 读 + PostgreSQL + k6 本体（Go，约 1 核）。
实测端到端 750ms–1.1s，说明有效算力远低于 4 核（k6/PG 争用），这也是 `docs/61 §10.2.9`
反复观察到「同配置 run 间 p95 711→1176ms 波动」的原因。

**因此现行门槛在 GitHub 免费 runner（4 vCPU、k6 同机）上不是「调优能否达标」的问题，
而是「测量装置本身超出被测机算力预算」**。

### 2.4 修复后复跑（run `42863847703`，4 vCPU / 4 worker，启动预热 + 冻结快照缓存后）

| 指标 | 修复前 `42859094367` | 修复后 `42863847703` |
|---|---|---|
| k6 `read_p95` p95 | 37.5ms | **19.8ms ✅** |
| k6 `save_p95` p95 | 1006ms | 538.4ms ❌ |
| k6 `session_start_duration` p95 | 1176ms | 796.5ms ❌ |
| 服务端 save p95（全量） | 1026ms | 529.6ms |
| **服务端 save p95（跳过前 40s warm-up）** | — | **264.6ms ✅** |
| **服务端 read p95（跳过前 40s warm-up）** | — | **18.8ms ✅** |

各波保存（每 30s 一波 100 并发）：t≈20s **470.4ms** / 104.2 / 89.7 / 41.4 / 34.0 / 79.3ms（p50）。

**这就是本提案的核心理由**：稳态已经达标（264.6ms），仍然判红的是「第一波保存 + 同秒 100 个
开考建会话」被混进同一个数字。要么给机器（提案 B），要么把三件事分开量（提案 A）。

## 3. 三个候选口径（供 R0/QA 选）

### 提案 A（推荐）：三档度量 + 明确资源前提

把一条门槛拆成三条，各自有语义与资源前提，**不放松任何真实用户体验**：

| 档 | 到底测什么 | 负载与窗口 | 建议门槛 | 依据 |
|---|---|---|---|---|
| **R1 稳态读写** | 学生日常作答/刷新 | 100 写 VU + 100 读 VU，**跳过前 40s warm-up 后统计**，3 min | save p95 < 300ms、read p95 < 300ms、失败率 < 0.1% | 修复后实测 **save 264.6ms / read 18.8ms，已达标**（§2.4） |
| **R2 保存突发** | 每 30s 一波的集中保存 | 100 并发保存/波 × 5 波（跳过第 1 波） | p95 < 500ms、p99 < 1s | 修复后 5 波 p50 = 104/90/41/34/79ms、p95 = 283/293/95/84/283ms（§2.4），留余量给坏 run |
| **R3 开场突发** | 100 名学生同秒开考 | 100 个 `POST /sessions` 同一秒（真实开考窗口） | p95 < 1s、p99 < 1.5s、失败率 < 0.1% | 进场是「一次性、可感知」事件；4 vCPU 实测 p95 796ms，8 vCPU 预期更低，留 200ms 余量 |
| 资源前提 | —— | **≥8 vCPU + SSD**；k6 与 API 不同机（或 k6 限制 ≤1 核且不计入被测机预算） | —— | §2.3 |

### 提案 B：保留单一门槛，但**钉死运行环境**

`p95<300ms` 不变，但把 CI perf job 迁到 **≥8 vCPU** 的 runner（自托管/付费 larger runner），
并要求 k6 与 API 分机。这是最「原教旨」的路径，代价是需要一台 8 核 Linux 机器（一次性或长期）。

### 提案 C（不推荐）：把阈值放宽到 800ms

不推荐：它会让「稳态保存变慢 2.7×」也判绿，丢掉门槛的回归价值。若最终只想改一个数字，
应该改的是**度量对象**（提案 A），不是**容忍度**。

## 4. 需要 R0/QA 拍板的三个问题

1. **选哪个提案**：A / B / C？若选 A，R1/R2/R3 的数值是否接受（表内为建议值）？
2. **资源标准**：生产/验收的最低规格是 4 vCPU 还是 8 vCPU？（当前 4 vCPU 的实测结论：
   稳态读写可行，同秒 100 开考 burst 不可行）——这直接决定 §3 的资源前提是否成立。
3. **是否允许「预热窗口不计入统计」**：这是压测行业惯例（warm-up），且我们已把冷启动
   提前到进程启动阶段；若不允许，则 R1 也要包含冷启动，需另行说明理由。
